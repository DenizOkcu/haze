Sandboxing & boundaries.

Model-initiated shell commands run inside an OS-level filesystem sandbox: Seatbelt on macOS, bubblewrap on Linux. The default boundary is the project you opened — not your home directory, not your secrets.

The boundary

Every command the shell tool runs — foreground or registered background — is spawned through the OS sandbox when a backend is available. The grep runner uses the same boundary as defense in depth. The boundary is a plain allowlist:

read-writeThe workspace (the directory you launched haze in), the temp directory, and tool caches (~/Library/Caches on macOS; ~/.cache and ~/.npm on Linux) plus any rwRoots you configure.
read-onlyPlatform-standard system directories (/usr, /opt, /Library, /System, /Applications, …), everything on your $PATH plus its bin-parent toolchain trees (homebrew, nvm/volta, cargo, sdkman-style layouts — derived from your login environment, not a per-tool list), your shell and node install trees, ~/.gitconfig, the ~/.haze and ~/.claude config dirs (credentials masked — see below), and every path you blessed that turn.
deniedEverything else: ~/.ssh, ~/.aws, shell histories, other projects, /etc writes. On macOS violations fail with EPERM; on Linux the paths simply do not exist.

Both backends evaluate canonical paths, so a symlink inside the workspace pointing at ~/.ssh does not smuggle reads — the resolved target is outside every allow. Re-invoking sandbox-exec or bwrap from inside can only tighten, never loosen.

Blessed paths

When you type @../shared-libs or any path containing a slash, the existing read-bless system grants the file tools a read for that turn. The sandbox honours the same user intent: blessed paths become read-only roots for sandboxed commands during that turn. Blessing never grants writes — the same rule the file tools follow, now enforced by the operating system. The model cannot bless anything itself; only your keystrokes grow the boundary.

Credential masks

Mounting ~/.haze and ~/.claude read-only is haze's choice, so their credential-bearing files are masked inside the mount: settings.json/settings.local.json (provider API keys), ~/.haze/sessions and ~/.claude/projects (transcripts), ~/.haze/logs, ~/.haze/history, and ~/.claude/.credentials.json. On macOS an explicit profile deny wins; on Linux those files are bound to /dev/null. A sandboxed cat ~/.haze/settings.json reads an empty file — keys never reach command output.

Workspace-internal secret files such as .env stay readable from sandboxed shells on purpose: source .env && npm test is a legitimate workflow. The file tools' hard secret refusal and the system-prompt rule own that layer.

Profiles & modes

workspaceDefault profile. Network allowed (npm/pip/cargo need it), caches writable.
strictNetwork denied entirely (bwrap unshares the network stack; Seatbelt denies network*), no cache writes. For offline audits.
autoDefault mode. Sandbox when a backend is available; degrade visibly (one notice per session) when not.
onRequire a backend. Commands refuse to run unsandboxed (sandbox_unavailable) with a platform remedy.
offNever sandbox. File-tool confinement still applies.

Controlling it

/sandbox prints the backend, mode, profile, and every root; /sandbox auto|on|off|workspace|strict|reset overrides the session (in-memory only, like /reasoning); /sandbox test runs live boundary probes. --sandbox <value> applies to a single interactive or print-mode run. Persistent configuration is the sandbox block in ~/.haze/settings.json:

{"sandbox": {"mode": "auto", "profile": "workspace", "roRoots": ["~/dev/docs"], "rwRoots": ["~/scratch"]}}

Paths outside the boundary need an explicit grant — either persistent via /sandbox grant <path> / /sandbox grant --rw ~/<module-cache> (revoked with /sandbox revoke), or session-scoped via /add-dir <directory>, which additionally lets the file tools read and edit inside the directory until the session ends. Grants are read-only by default with the confirmation disclosing that credentials inside the path become readable; protected-secret paths are refused. When a command fails at the boundary, the result carries a sandbox_boundary reason naming the exact grant that would fix it. Toolchains on $PATH and platform-standard directories are read-only by default and need no grant.

Platform support

macOS uses Seatbelt (sandbox-exec) with a generated deny-by-default profile. Apple deprecates the tool but still ships it; haze probes availability and degrades visibly if it disappears. One platform caveat: OS credential stores (the macOS Keychain) cannot be reached from inside the sandbox — tools that keep credentials there need a file-based credential layout (most CLIs offer one) combined with a config-dir grant, or /sandbox off for those commands. Linux uses bubblewrap with an explicit mount tree: a private empty $HOME (npm writes its dotfiles there), config dirs re-mounted read-only on top, /tmp as a per-command tmpfs; file-based tool credentials work through grants the same way. bwrap requires unprivileged user namespaces or a setuid install; Ubuntu 23.10+ restricts the former, and the diagnostics explain the remedy. Windows has no backend: auto degrades to off with a notice, on fails closed.

What it is not

The sandbox confines filesystem reach of model-initiated child processes. It does not confine the haze process itself (provider calls, ~/.haze writes), LSP or MCP servers (user-configured infrastructure), CPU/memory resources, or network egress in the default profile. It is not a permission gate — there are no approval dialogs; the boundary either allows, or fails with an actionable error you can override as the user. Attended expert use remains the operating model; treat it as a blast-radius reduction, not an isolation guarantee.
